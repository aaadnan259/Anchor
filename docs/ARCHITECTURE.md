# ARCHITECTURE.md — Software Structure

How Anchor is **built**. Product behavior belongs in `PROJECT_SPEC.md`; engineering rules in `../CLAUDE.md`; the reasoning behind non-obvious choices in `DECISIONS.md`. This file describes the current shape, not why every alternative was rejected.

---

## Pattern

MVVM with dependency injection, strictly one direction:

```
Views → ViewModels → Services → SwiftData → Foundation
```

Allowed: View → ViewModel, ViewModel → Service, Service → Model.
Forbidden: View → SwiftData, View → UserNotifications, View → CoreLocation, View → Adhan, Service → UI, Model → Service. No circular dependencies.

| Layer | Responsible for | Never responsible for |
|---|---|---|
| **Views** | Layout, rendering, interaction, animation, accessibility | Calculations, scheduling, notifications, persistence, filtering business data |
| **ViewModels** | UI state, user intent, data transformation, calling services | Persistence implementation, notification scheduling, prayer calculations |
| **Services** | Business rules, scheduling, persistence, notifications, location, streak math | Anything UI. Stateless wherever practical |
| **Models** | Business entities only | Logic, networking, UI |

ViewModels are `@Observable @MainActor` and constructed fresh per screen in a `.task` block. Only Services (plus `SettingsService` and `LocationService`) are injected via `@Environment`, because those are genuinely shared and long-lived.

## Stack

iOS 17+ · Swift 6 (`SWIFT_STRICT_CONCURRENCY: complete`) · SwiftUI · SwiftData · Observation · Foundation · CoreLocation · UserNotifications · Swift Charts. Project generated by XcodeGen from `project.yml`. One external dependency, Adhan Swift, permitted only because Apple provides no prayer-calculation API — never exposed outside `PrayerService`.

## Folder Structure

Under `Anchor/`: `App/`, `Models/`, `ViewModels/`, `Views/`, `Components/`, `Services/`, `Theme/`, `Utilities/`, `Extensions/`, `Assets.xcassets/`, `Preview Content/`. Tests in `AnchorTests/`. Never add a top-level folder.

## Data Model

Four SwiftData `@Model` classes. Everything else is derived — **never persist a calculated value.**

**`Habit`** — `id`, `name`, `icon` (SF Symbol name *or* a single emoji; `String.isSFSymbolCompatible` picks the renderer), `accentColor` (one of the 8 curated cases, always set), `customColorHex` (optional; exact color that overrides `accentColor`), `reminderEnabled`, `archived`, `createdAt`, `displayOrder`, `targetValue` (optional numeric daily target; `nil` for binary habits), `unit` (optional label for the target). Computed: `tintColor` → `customColorHex` if set, else `accentColor.color` — **read this, never `accentColor.color` directly**, or an active custom color is ignored. `frequency` is a computed accessor over privately-stored JSON `Data`, not a stored property.

**`Occurrence`** — one completion opportunity (Fajr, Breakfast, Evening Walk). `id`, `title`, `displayOrder`, `habit` (relationship), `scheduleProvider` (computed accessor over stored JSON `Data`).

**`Completion`** — `id`, `day`, `completedAt`, `value` (defaults to 1; compared against `Habit.targetValue` for quantifiable habits), `habit` and `occurrence` relationships.

**`Shield`** — one day a habit is exempt from breaking its streak. `id`, `day`, `habit` (relationship). Habit-day granularity only — it protects the whole habit for a day, never a single occurrence. Meaningful only for Daily/Weekdays habits (`Frequency.supportsShields`); never persist one for a `.timesPerWeek` habit. Never counted as a completion; read only by `StreakService` and the history views.

Relationships cascade from `Habit` → `Occurrence` / `Completion` / `Shield`, and `Occurrence` → `Completion`.

## Services

**`CompletionService`** — **the single choke point for "is this done."** Owns `isCompleted`/`isFullyCompleted` (occurrence- and habit-level, threshold-aware for quantifiable habits), `value`, `completedDayCount`, `toggle` (binary) / `logValue` (quantifiable), `isShielded`/`toggleShield`. Every other service or view model that needs completion state calls through this — never re-implemented elsewhere. See ADR-002.

**`HabitService`** — create, edit, update an occurrence's schedule provider, archive, delete, duplicate, reorder, fetch.

**`ScheduleService`** — returns today's occurrences, using `ScheduleProvider` internally.

**`StreakService`** — current streak, best streak, completion rate, weekly progress, `dailyHistory` (trailing window, for the heatmap) and `dayCompletionState` (single arbitrary day, for Calendar History). Reads `CompletionService`'s completion and shield checks; never re-implements either.

**`InsightsService`** — `trend` (week/month/year buckets), `timeOfDayDistribution` (Night/Morning/Afternoon/Evening), `weekdayDistribution` (per-weekday completion rate). Reads `CompletionService` and `DueDateRule`; never re-implements completion logic.

**`PrayerService`** — the only wrapper around Adhan. Never expose Adhan types outward.

**`LocationService`** — owns CoreLocation; requests permission only when a Prayer schedule exists.

**`NotificationService`** — schedules local notifications; never called directly from Views.

**`ExportService`** — stateless, operates on a passed-in `[Habit]` with no `ModelContext` dependency. CSV (flat, one row per completion) and JSON (nested per habit). Includes archived habits; never special-cases habit type.

**`AuthenticationService`** — wraps `LocalAuthentication`. `LAContext`/`LABiometryType` never leak outside this file. `authenticate()` uses `.deviceOwnerAuthentication` (biometrics *with* passcode fallback), never biometrics-only.

**`SettingsService`** — UserDefaults-backed app-wide preferences.

## Scheduling

Never special-case Prayer. A strategy pattern answers "what is today's schedule":

```
ScheduleProvider ← FixedTimeProvider · PrayerProvider · WeeklyProvider
```

plus the shared `DueDateRule` ("is this habit due on this day"). Views never know where a schedule originates.

## State Management

Prefer, in order: `@State` → `@Binding` → `@Bindable` → `@Environment` → `@Query`. Avoid `ObservableObject` (zero exist; everything is `@Observable`). Never duplicate state — keep a single source of truth.

## Concurrency

Swift 6 strict concurrency. Services and ViewModels are `@MainActor`. Apple framework types predating Sendable auditing (`UNUserNotificationCenter`, `LAContext`) are wrapped behind `@preconcurrency import` in the single file that touches them, never leaked outward.

## Persistence

SwiftData only, for `Habit`/`Occurrence`/`Completion`/`Shield`. No backend, no accounts, no iCloud. App-wide scalar preferences (appearance, accent color, prayer calculation method, biometric lock, smart reminders) go through `SettingsService` into UserDefaults — deliberately a separate mechanism, since they're settings, not relational business data. Don't mix the two.

## Navigation

Root branch in `AnchorApp`, in order:

1. Test host (`XCTestConfigurationFilePath` present) → straight to `RootTabView`, no gating.
2. `!hasCompletedOnboarding` → `OnboardingView` (one-time full-screen flow).
3. `biometricLockEnabled && !isUnlocked` → `LockScreenView` (re-locks on every background→foreground).
4. Otherwise → `RootTabView`.

`RootTabView` has three tabs: Today, Habits, Stats.

**Sheets:** Add/Edit Habit (from Today, Habits), Settings (Today's gear), Log Value (Today, quantifiable habits only), Manage Shielded Days (Habit Insights).
**Push:** Stats → Habit Insights → Calendar History.
**Quick action, no navigation:** long-press a Today card → Shield Today / Remove Shield (Daily/Weekdays only).

Three levels deep is a deliberate, considered exception to the previous two-level limit: Calendar History is a terminal leaf and a pure browse view of data Habit Insights already shows more compactly. If a feature needs a fourth level — or a third that isn't a terminal leaf — reconsider whether it belongs in Anchor at all.

## Notifications

Recalculate on app launch, foreground, midnight, habit edit, location change, and notification-settings change. Keep only the next 7 days scheduled. Never duplicate notifications.

## Location

Optional. Requested only when a Prayer schedule exists. If denied: the Prayer habit still works, its notifications are disabled, and the UI shows helpful guidance — no blocking alerts.

## Design System

Tokens live in `Anchor/Theme/`: `Spacing` (4/8/12/16/24/32/48), `CornerRadius` (`.small` 12 for controls, `.card` 20 for cards — always `.continuous`), `Surface` (semantic background/card/border), `Typography` (named SF Pro `Font` extensions), `Motion` (named animation presets), `AccentColor` (the curated 8). No ad-hoc values anywhere. **No `.shadow()` anywhere** — depth comes from color, opacity, and stroke, deliberately. Haptics fire on meaningful state changes only, never on passive navigation.

Reusable components carry the UI vocabulary: `ProgressRingView` (opt-in `pulseGlow`), `HabitCardView`, `HabitIconView`, `CompletionToggleView`, `IconPickerView`, `AccentColorPickerView` (8 curated swatches + 1 custom via native `ColorPicker`), `SectionHeaderView`, `PrimaryButtonView`, and the chart/history set. `HabitHistoryGridView` (dot-matrix heatmap) and `CalendarHistoryGridView` (month grid) are distinct presentations of the same `DayCompletionState` data and share one color mapping, `DayCompletionState.color(tint:)` — neither defines its own. Don't duplicate UI.

## Performance

Target 60 FPS and sub-one-second cold launch where practical. No expensive work in `View.body`. Lazy containers for large collections. Minimal SwiftData queries. Cache today's prayer calculations. Measure before optimizing.

## Extensibility

Future features should fit this architecture rather than reshape it — a widget would consume `ScheduleService`, a watch app `HabitService`, iCloud the persistence layer. Ten-plus major features have landed without an architecture change. Extend existing systems; don't rewrite them.

## Anti-Patterns

Never: business logic in Views · duplicated state · singleton managers · exposing Adhan · persisting calculated values · special-casing Prayer · features outside `PROJECT_SPEC.md` · dependencies without approval · rewriting working code without measurable benefit. Code-quality rules (no force unwraps, graceful recovery, accessibility) are in `../CLAUDE.md`.
